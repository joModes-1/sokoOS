# Non-Functional Requirements

Requirement IDs NFR-001–NFR-015 are reused from `docs/01-executive-summary.md` and `docs/03-cleaned-srs.md` and are not renumbered. Every target is measurable, and every row is verified by an automated check or a documented manual check. Deferred scope (Phase 3 Supplier ecosystem, Phase 4 Finance, Phase 5 AI capabilities, Phase 6 Expansion, the React Native app, patient medical records) carries no NFRs in this release.

## Non-Functional Requirements

| ID | Category | Requirement | Rationale | Target | Verification |
|---|---|---|---|---|---|
| NFR-001 | Performance | The API shall respond within p95 500 ms for reads and p95 1 s for writes at 50 concurrent users. | POS, stock and dashboard screens are used on shop-floor devices during live trading; slow responses block the till queue. | p95 ≤ 500 ms reads, p95 ≤ 1 s writes, p99 ≤ 2 s at 50 concurrent users with MVP data volumes (≤ 50,000 products and ≤ 1,000,000 stock movements per tenant). | k6 load test against staging before each release; latency panels from centralized logging; release gate on > 20% regression versus the recorded baseline. |
| NFR-002 | Scalability | The architecture shall be a modular monolith with a stateless API, database connection pooling, pagination and indexed queries, retaining a path to horizontal scaling. | MVP is built by one developer with an AI coding agent; microservices are explicitly avoided until scaling requires them. | 50 concurrent users at launch with a tested path to 500 concurrent users by adding API instances and a read replica; every list endpoint paginated with default page size 25 and maximum 100; 0 unbounded queries in review. | Architecture review checklist; load test at 50 and 250 concurrent users; query-plan review of the 20 highest-traffic endpoints. |
| NFR-003 | Reliability | The production system shall target 99.5% monthly availability, subject to the hosting provider tier. | Sales, stock and payment flows are business-critical during trading hours; downtime stops tills. | 99.5% monthly uptime = ≤ 3 h 39 min unplanned downtime per 30-day month; `/v1/health` returns HTTP 200 within 2 s. | Uptime monitoring with 1-minute checks and alerting; monthly availability report from the hosting provider. |
| NFR-004 | Backup/Recovery | The system shall take daily automated database backups retained for 14 days, and backup restoration shall be tested in staging before launch. | The stock ledger, sales and payment records are the tenant's book of record and cannot be reconstructed from any other source. | 1 automated backup per 24 h; 14-day retention; RPO ≤ 24 h; RTO ≤ 4 h; 1 documented successful restore drill in staging before launch and 1 per quarter thereafter. | Backup job logs; restore drill record with timestamps and row counts; release gate on verified restore. |
| NFR-005 | Security | The system shall have no unresolved P0 or P1 findings from security review at launch, with server-side authorization on all protected endpoints. | Tenant isolation, financial records and personal data are the highest-value assets; RBAC and branch restrictions must be enforced server-side. | 0 unresolved P0/P1 findings; 100% of protected endpoints covered by server-side RBAC and tenant-scope tests; 0 critical or high dependency vulnerabilities at release; 0 secrets committed to the repository. | Security review checklist; automated SAST and dependency scan in CI; authorization integration tests for all 4 roles (Business Admin, Branch Manager, Cashier, Inventory Clerk). |
| NFR-006 | Data integrity | The system shall enforce data integrity through database transactions for every stock, money and state transition, idempotency keys on sale submission and provider event ids on callbacks. | The stock movement ledger is immutable, balances must reconcile to the ledger, and no overselling or duplicate payment is permitted. | 0 duplicate sales and 0 duplicate stock movements across 1,000 repeated idempotency-key submissions; 0 balance drift between `inventory_balances` and the sum of `stock_movements` in the reconciliation test; 100% of state transitions wrapped in a transaction. | Integration tests for sale+inventory, PO+receiving, transfers and payment reconciliation; stock reconciliation report asserting closing balance = sum of movements. |
| NFR-007 | Observability | The system shall provide centralized application logging, error monitoring and audit logs containing actor, action, target, timestamp and context, and shall never log passwords, tokens or full payment credentials. | Payment and stock incidents must be diagnosable from logs alone; audit logs are a compliance and dispute-resolution requirement. | 100% of API requests logged with requestId, route, method, status, latency, tenantId and userId; 100% of critical actions written to `audit_logs` with actor, action, target, timestamp and context; 0 passwords, tokens or full payment credentials in logs; error alerts delivered within 5 minutes. | Log audit against the redaction checklist; alert delivery test; audit-log coverage test against the critical-action list. |
| NFR-008 | Accessibility | All authenticated screens shall meet WCAG 2.1 Level AA. | Shop attendants and administrators use the product for full shifts; accessibility also improves usability on small screens and with barcode scanners. | 0 critical or serious axe violations on the 10 core flows (sign-in, dashboard, product list, stock list, stock adjustment, transfer, purchase order, goods receipt, POS sale, day closure); 100% of interactive controls keyboard reachable with visible focus. | Automated axe scan in CI on the 10 core flows; manual screen-reader pass on POS sale and stock adjustment before launch. |
| NFR-009 | Compatibility | The web application shall support the last two versions of Chrome, Firefox and Edge, Safari 14 or later, and current Android Chrome, and shall be installable as a PWA. | Users work on mixed desktop and Android devices, frequently on low-bandwidth connections. | 5 critical flows (sign-in, POS sale, stock list, goods receipt, day closure) pass on 5 browser targets; PWA installability passes with a service worker and web app manifest; first contentful paint ≤ 3 s on a throttled 3G profile. | Cross-browser smoke suite on the 5 flows; Lighthouse PWA and performance run per release. |
| NFR-010 | Maintainability | The codebase shall carry unit tests for stock, pricing, tax, refund, purchase order, payment, forecasting and permission logic, integration tests for sale+inventory, PO+receiving, transfers, supplier lifecycle, payment reconciliation, import and AI authorization, and E2E scenarios A–G. | One developer with an AI coding agent must change financial and stock logic safely; regressions in these areas are unrecoverable in production. | ≥ 80% line coverage on backend domain modules (stock, pricing, tax, refunds, payments, permissions); 100% of the listed integration suites present and green; E2E scenarios A–G green in CI on every merge. | CI coverage report; test suite results; release gate on green suites. |
| NFR-011 | Error handling | All API errors shall return the shape `{ error: { code, message, details, requestId } }` with no stack traces or secrets in production responses. | Cashiers and clerks need actionable messages, and leaked internals are a security risk. | 100% of 4xx and 5xx responses conform to the error shape; 0 stack traces, SQL fragments or secrets in production responses; every error response carries a requestId traceable to exactly 1 log entry. | API contract tests for the error shape; staging review of 5xx responses; log correlation check by requestId. |
| NFR-012 | Localization readiness | The MVP shall be English-only and i18n-ready, with all user-facing strings externalized, UTC timestamps in API responses and USD as the display currency. | Expansion beyond Uganda is deferred but must not require rewriting the UI; a tenant may trade in a currency other than the display default. | 0 hardcoded user-facing strings in reviewed components; 100% of API timestamps in ISO-8601 UTC; 1 currency per tenant with USD as the default display currency; all monetary values stored as integers in minor units. | Lint rule and code review for hardcoded strings; API response review; schema review of money columns. |
| NFR-013 | API versioning | All endpoints shall be versioned by URL prefix `/v1/` and documented with OpenAPI; breaking changes require a new version prefix. | A future React Native app and tenant integrations must not break on internal refactors. | 100% of endpoints under `/v1/`; OpenAPI document covering 100% of endpoints, regenerated on every build; 0 breaking changes inside a published version. | OpenAPI diff check in CI; API review checklist; contract tests run against the published spec. |
| NFR-014 | Compliance | The system shall comply with the Ugandan Data Protection and Privacy Act 2019 and relevant regulations for personal, financial and business registration data. | The platform stores personal data (users, customers, suppliers), financial records and business registration and tax information. | 100% of personal, financial and registration data fields classified in the data inventory; 0 sensitive fields readable outside the owning tenant and permitted roles; data subject access, correction and deletion requests completed within 30 days (Assumption: 30-day response window per the Act); audit entries retained for the life of the tenant record. | Data inventory review; access-control tests per role; data subject request procedure walkthrough before launch. |
| NFR-015 | Release gates | Release shall be gated on financial correctness, stock reconciliation, duplicate prevention, E2E scenarios, verified backups and import error handling. | These six areas are the failure modes that destroy tenant trust and cannot be corrected after the fact. | 6 of 6 gates green before any production deploy: financial totals match stored sales and refunds exactly; stock reconciliation drift = 0; duplicate sales and movements = 0; E2E scenarios A–G pass; 1 verified backup restore in staging; import error report produced for 100% of invalid rows. | Release checklist executed in CI and recorded in the deploy log; any failed gate blocks the deploy. |
